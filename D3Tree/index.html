A block-diffusion drafter proposes a whole tree of candidate tokens almost for free, but every node it sends to the target model takes a query row in verification. D3Tree decides how much of that tree to verify at every decoding step: the whole tree when the GPU has room, and under concurrent load only the most promising nodes of the whole batch, sized to the target's matrix-multiplication tiles.

01 · The problem

Every candidate costs a verification row

DFlash drafts a block of positions in one pass, and DDTree turns its position-wise marginals into the \(B\) most probable prefixes. A deeper or wider tree raises the expected number of accepted tokens, yet the target must process every node, although only one path is committed. With one request the target pass is bound by reading the weights, so extra rows are nearly free. With many requests the batch width sets the cost, and low-yield branches delay every request in the batch.

CaDDTree picks the tree size from a latency table, but that table is profiled offline for a single request: the size it chooses does not react to how many requests share the step. D3Tree instead decides from the batch it is actually verifying.

04 · Method · node survival and pruning

A threshold on path survival keeps an ancestor-closed subtree

A tree-size head with \(2H{+}2\) parameters scores each candidate with the probability \(q(v)\) that it matches the target continuation given that its parent does. Path survival \(S(v)\) is the product of \(q\) along the parent chain, so it never rises from parent to child, and every threshold \(\delta\) keeps a subtree that contains the ancestors of each retained node. CaDDTree, in contrast, verifies a prefix of the drafter's best-first order. Try both on the paper's running example: the target continues with tea with lemon.

\[S(0)=1,\quad S(v)=S(\pi(v))\,q(v)=\prod_{u\in\mathcal{P}(v)}q(u),\qquad \mathcal{T}_{B,\delta}=\{0\}\cup\{v\in\mathcal{T}_B\setminus\{0\}:S(v)\geq\delta\},\qquad W=N+1\]

Left: each node sits at its depth and its path survival \(S(v)\) on a log scale; D3Tree keeps the nodes above \(\delta\). Right: the same seven candidates in best-first order of the draft path score; CaDDTree keeps the first \(B^\ast\) of them. \(W\) counts target query rows including the root; accepted tokens follow the target path tea → with → lemon. 05 · Method · load-dependent allocation

One node budget for the whole batch, sized to the GEMM tile

The target's matrix multiplications process query rows in tiles of \(s=64\) rows on an RTX 6000 Ada: latency is nearly flat inside a tile and jumps by 12–30% when the width crosses a multiple of \(s\). Up to \(R_{\mathrm{full}}\) requests D3Tree verifies whole trees. Beyond it, the step threshold \(\delta_t\) is the \(N_{\mathrm{tot}}\)-th largest path survival in the batch, and the budget \(N_{\mathrm{tot}}\) fills the last tile that the roots and \(\bar n(R)\) nodes per request reach. Hybrid targets with gated DeltaNet layers start pruning earlier.

\[\delta_t=\begin{cases}0, & R\leq R_{\mathrm{full}},\\ S_{(N_{\mathrm{tot}})}, & R>R_{\mathrm{full}},\end{cases}\qquad N_{\mathrm{tot}}(R)=s\left\lceil\frac{R\,(1+\bar n(R))}{s}\right\rceil-R\]

Rows verified in one decoding step for \(R\) concurrent requests with a 15-node construction budget. Shading marks the tiles the step occupies; vertical lines are tile boundaries of 64 rows. CaDDTree uses its measured size on Q3.5-4B at \(B=31\) (26 nodes per request, the same at every load). D3Tree follows the paper's allocation table: whole trees up to \(R_{\mathrm{full}}=8\) (4 for hybrid targets), then \(\bar n=7\) nodes per request below \(R=24\) and \(\bar n=5\) above, rounded up to fill the last tile. Ties at the threshold can add a few nodes in the real runtime.

06 · Results · six verifiers, 17 benchmarks

Fastest from one request to sixty-four

All strategies for a verifier share the same drafter, prompts, generation limits and serving runtime; only the draft tokens sent to the target differ. Speedup divides output throughput by that of autoregressive decoding on the same GPU and prompts. Pick a verifier, a benchmark group and a metric; hover the chart for values.

Single request, per benchmark. Darker cells are higher within each benchmark; the outlined cell is the best strategy for that benchmark. At \(R=1\) D3Tree verifies the same whole trees as DDTree \(B=15\) (equal \(\tau\)); its margin there comes from GPU-resident construction and overlapped execution.

Other GPUs. On an A800 with all six verifiers, D3Tree is the fastest strategy in 61 of the 72 settings (allocation table retuned for \(R\geq16\) on that GPU); every exception is DSpark, mostly on the hybrid Qwen3.5 targets under heavy load, where the per-step cost of tree verification, not the number of verified tokens, decides. On an RTX 5090 it is the fastest in 31 of the 36 settings for Q3.5-4B, IVL3.5-4B and G4-E2B; on the smallest verifier, G4-E2B, DFlash's linear draft is ahead up to \(R=8\), and D3Tree leads from \(R=16\) on.

07 · Serving over time · paper Figs. 5–6

The allocation at work

The speedup tables summarize each run by one number per load. To see what happens inside a run, the scheduler records, at every decoding step, the requests in flight and the draft tokens each of them verifies. With 200 requests served at a fixed concurrency of 64 (Q3.5-9B, RTX A6000), D3Tree finishes first, after 132 s at 1,301 output tokens/s, ahead of DSpark (135 s) and autoregressive decoding (139 s). DFlash, DDTree and CaDDTree need 192–215 s: each of their target passes processes about 1,010 tokens, against 382 for D3Tree. As the last requests finish, D3Tree widens its trees again, up to whole 15-node trees for the last four.

In serving, the load changes within seconds. A phased Poisson trace of 420 requests (0.6–10 requests/s, at most 64 in flight) exceeds what one A6000 serves with this verifier under every strategy, so latency is set by how fast each strategy drains the queue. D3Tree has the lowest mean latency in all seven arrival phases: 55.3 s over the trace, against 58.8 s for DSpark, 73.8 s for autoregressive decoding and 119–147 s for the fixed-width strategies. Under heavy load it verifies about as many draft tokens per request as DSpark (5.2 vs 4.8) yet accepts more of them (4.09 vs 3.75 per round), because it keeps the most promising nodes of the whole batch rather than a prefix of each chain.

08 · Conclusion

Verify what the batch can afford

We presented D3Tree, which decides how much of a block-diffusion draft tree to verify. A tree-size head with \(2H{+}2\) parameters scores every candidate, parent-chain products yield an ancestor-closed subtree, and a batch-wide node budget aligned with the target's matrix-multiplication tiles sets how many nodes each decoding step verifies. Under light load, D3Tree verifies whole trees; as concurrency grows, it spends one budget across the batch instead of a tree size fixed per request in advance. On six vision-language verifiers and 17 text and multimodal benchmarks, D3Tree is the fastest of the compared verification strategies in 70 of 72 load settings, reaching 3.2–4.0× over autoregressive decoding for a single request and 1.3–1.8× at 64 concurrent requests, where fixed-budget trees fall below autoregressive speed. In serving, it completes a fixed-concurrency workload first and attains the lowest mean latency in every phase of a time-varying arrival trace. Two limitations remain. On the A800, the per-step cost of tree verification on hybrid targets, namely tree attention and the replay of recurrent states, lets dynamically truncated chains overtake D3Tree under heavy load; closing this gap calls for cheaper tree kernels rather than a different allocation. In addition, our verification is greedy. Extending tree pruning to stochastic sampling, and evaluating the optional joint training of the drafter at scale, are left to future work.
